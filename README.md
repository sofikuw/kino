# kino

**A Material 3 movie and TV app for iOS.**

Named for *kino* — It streams from **MovieBox**, and it
is built in the open about what that means rather than around it.

## Status: step one

This repository is deliberately small. It does **one** thing:

> Press a button, sign in to MovieBox, and see whether it worked.

No search, no rails, no player, no watchlist. That is the point.

The previous draft of this app carried five screens and a client with search,
details and streams — none of which could be compiled where it was written, and
one of which contained an infinite recursion that would have crashed on launch.
It was deleted. What replaced it is the smallest thing that proves the hard part
works.

If the button returns a green card with a token expiry, then four things are
true at once, on a real device:

- Material 3 is wired up
- HMAC-MD5 in Dart matches the server
- The region gate is cleared
- The network path works from iOS

Those four are the foundation. Everything else is UI on top of a working client.

## Building

The IPA is unsigned; signing and installing it is separate.

**Actions → Build and Release iOS → Run workflow**, channel `alpha`.

Every run generates its own tag with a random suffix (`kino-v1.0.0-alpha.4f2ab9`)
and publishes a prerelease, so the workflow can be re-run without editing
`pubspec.yaml`.

### Why the workflow runs `flutter create`

This repo does not contain `ios/Runner.xcodeproj`, `Info.plist` or a `Podfile`.
Those are generated by Flutter, contain Xcode-internal UUIDs, and hand-writing
them produces a project that looks complete and does not build.

The environment this app was authored in has no Flutter — so the scaffolding is
generated **in CI**, on every run, and the Dart here is grafted onto it. The
`pubspec.yaml` is copied over the scaffold's *after* scaffolding, because
`flutter create` writes its own and would otherwise silently replace it.

## How MovieBox authorisation actually works

Two gates, in order. Both were established by **measuring the live API**, not by
reading someone's source — and the difference matters, because the obvious
reading turns out to be wrong.

### Gate 1 — region

A bare request gets:

```
403 FORBIDDEN  "Service not available in current region"
```

from every host, from anywhere. Adding `x-client-info` — one JSON header
describing an Android app — clears it, **regardless of the real connection IP**.

That last part is worth stating plainly: the API trusts the header over the
connection. So there is no proxy, no VPN and no IP spoofing in this client. A
spoofed `x-forwarded-for` was tested and changes nothing, so it is absent here on
purpose rather than by omission.

### Gate 2 — signature

With `x-client-info` present, the answer becomes:

```
407 Unauthorized  "Signature invalid"
```

until the request is signed. The scheme:

```
x-client-token  = "<ts_ms>,<md5hex(reverse(str(ts_ms)))>"
x-tr-signature  = "<ts_ms>|2|<base64(hmac_md5(secret, canonical))>"

canonical = join("\n", [
  METHOD.toUpperCase(),
  accept,
  content-type,
  body_length,              // decimal BYTE count, "" when no body
  ts_ms,
  md5hex(body[0..102400]),  // "" when no body
  "/path?sorted_query",     // query params sorted by key
])
```

**HMAC-MD5, not SHA-256.** `package:crypto` exports `Hmac` for the SHA family
only, so this is hand-built from the raw `Md5` digest in
[`lib/core/moviebox/signer.dart`](lib/core/moviebox/signer.dart).

The algorithm was implemented in Node first and **run against the live API**: it
returns `HTTP 200` and a visitor token with a three-month expiry. So the
constants and field order here are measured, not inferred.

## What this is, honestly

`kino` streams from a service that gates by region and by device, and the client
impersonates that service's own Android app to get through. The secret key is a
constant published in someone else's public repository.

Three consequences worth naming rather than burying:

1. **The secret can be rotated at any time.** When it is, every installed build
   stops working, and nothing client-side can compensate. That is a property of
   the approach, not a bug to be fixed.
2. **The service does not want this.** The region gate exists deliberately. This
   client answers it with a header rather than with a proxy — but it is still
   answering it.
3. **M3 is the only part of this that is unambiguously fine.** The theme, the
   layout and the code structure are ordinary app work.

Content is not hosted here. Users are responsible for their own compliance.

## Next steps

In order, each one building on something already proved:

1. **Search** — `POST /subject-api/search/v2`, already mapped
2. **Details** — `GET /subject-api/get`, plus season-info for series
3. **Streams** — `play-info/v2` and `resource`, merged and deduped
4. **Player** — requires a `Referer: https://sportslive.wine` header, which is
   why `media_kit` is a dependency and Flutter's own `video_player` is not: it
   cannot send headers on iOS at all
5. **Downloads** — a per-chapter manifest, as in the sibling project
