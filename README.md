# kino

**A Material 3 movie and TV app for iOS.**

Named for *cinephage* — a devourer of film. It streams from **MovieBox**, and it
is built in the open about what that means rather than around it.

## What it does

| Screen | What |
| --- | --- |
| **Home** | The rails MovieBox returns for a tab — their titles, their ordering. Pull to refresh. |
| **Search** | Debounced query against the API, results in a responsive grid. |
| **Details** | Poster, synopsis, seasons for a series, and a Play button. Bookmark to save. |
| **Player** | `media_kit`, with a quality picker built from the merged stream list. |
| **Watchlist** | Local, on-device. |

Two titles flows, decided by `subjectType`: a **film** plays with `subjectId`
alone; a **series** gets a season picker.

## Building

The IPA is unsigned; signing and installing it is separate.

**Actions → Build and Release iOS → Run workflow**, channel `alpha`.

Every run generates its own tag with a random suffix (`kino-v1.1.0-alpha.4f2ab9`)
and publishes a prerelease, so it can be re-run without editing `pubspec.yaml`.

### Why the workflow runs `flutter create`

This repo does not contain `ios/Runner.xcodeproj`, `Info.plist` or a `Podfile`.
Those are generated by Flutter, carry Xcode-internal UUIDs, and hand-writing them
produces a project that looks complete and does not build.

The environment this app was authored in has no Flutter — so the scaffolding is
generated **in CI**, on every run, and the Dart here is grafted onto it. Order
matters inside that step, and each line of it is there because getting it wrong
produced a specific failure:

- `pubspec.yaml` is copied **after** scaffolding, because `flutter create` writes
  its own and would silently replace the authored one.
- The scaffold's `test/` is deleted, because it instantiates `MyApp` — the demo
  app — and `flutter analyze` fails on a class this app does not have.
- `flutter analyze` runs before `xcodebuild`, because it is the only fast compile
  check in the pipeline.

## How MovieBox authorisation actually works

Two gates, in order. Both were established by **measuring the live API**, not by
reading someone's source — and the difference matters, because the obvious
reading turned out to be wrong.

### Gate 1 — region

A bare request gets `403 FORBIDDEN "Service not available in current region"`
from every host, from anywhere. Adding `x-client-info` — one JSON header
describing an Android app — clears it, **regardless of the real connection IP**.

That last part is worth stating plainly: the API trusts the header over the
connection. So there is no proxy, no VPN and no IP spoofing here. A spoofed
`x-forwarded-for` was tested and changes nothing, so it is absent on purpose
rather than by omission.

### Gate 2 — signature

With `x-client-info` present, the answer becomes `407 "Signature invalid"` until
the request is signed:

```
x-client-token  = "<ts_ms>,<md5hex(reverse(str(ts_ms)))>"
x-tr-signature  = "<ts_ms>|2|<base64(hmac_md5(secret, canonical))>"

canonical = join("\n", [
  METHOD.toUpperCase(),
  accept,
  content-type,
  body_length,              // decimal BYTE count, "" when no body
  ts_ms,
  md5hex(body[0..102400]),  // "" when no body
  "/path?sorted_query",     // query params sorted by key
])
```

**HMAC-MD5, not SHA-256.** `package:crypto` exports `Hmac` for the SHA family
only, so this is hand-built from the raw `Md5` digest in
[`lib/core/moviebox/signer.dart`](lib/core/moviebox/signer.dart).

Both gates were verified against the live API before any of this was written in
Dart: the first Dart run returned `HTTP 200` and a visitor token with a
three-month expiry.

### Response shapes — measured, not inferred

The client's parsing is unusually comment-heavy for one reason: an earlier draft
guessed at these and was wrong in ways that fail *silently*. Specifically:

- **`data.results[]` in search is a list of RAILS**, each with a nested
  `subjects[]` — not a flat list of titles. A parser expecting a flat list gets
  nothing and renders "no results" forever.
- **`subjectId` is a quoted String**, not a number.
- **`cover` is an object** carrying `url`, not a URL string. A parser expecting a
  string gets null and every card shows its placeholder.

None of those throw. All of them look like an empty catalogue.

## What this is, honestly

`kino` streams from a service that gates by region and by device, and the client
impersonates that service's own Android app to get through. The signing key is a
constant published in someone else's public repository.

Three consequences worth naming rather than burying:

1. **The key can be rotated at any time.** When it is, every installed build
   stops working, and nothing client-side can compensate. That is a property of
   the approach, not a bug.
2. **The service does not want this.** The region gate exists deliberately. This
   client answers it with a header rather than with a proxy — but it is still
   answering it.
3. **The Material 3 work is the only part that is unambiguously fine.** The
   theme, the layout, the state handling — ordinary app work.

Content is not hosted here. Users are responsible for their own compliance.

## Known gaps

- **Seasons are parsed defensively and may not render.** The `season-info`
  envelope was never measured — only search and home were. `seasonsOf` reads
  several plausible keys and returns an empty list rather than throwing, so a
  series page degrades to poster + synopsis rather than crashing. Measuring that
  endpoint is the next step.
- **No episode list.** A series plays season 1 episode 1. Per-episode
  selection needs the measured season shape first.
- **No downloads.** The sibling project's per-chapter approach would port here,
  but the stream list is not stable enough to build storage on yet.
- **The watchlist is local only.** The MovieBox token identifies nobody, so there
  is no server-side list to sync against — AniList-style tracking would need its
  own integration.
